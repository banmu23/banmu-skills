# Article Structure

## Default Structure

### Practical Skill Productization Structure

For posts about turning a workflow into a reusable Skill, prefer this structure:

```text
Title: short action chain, e.g. from material to draft box
Opening: show concrete finished outputs and links separately
Bridge: tell beginners the article will walk from zero to one
Tool entrances: official websites, docs, backend entrances, setup prompt
Workbench base: explain the simplest bridge between tools
First complex run: plan first, execute after confirmation
Material input: minimum useful material, not a luxury package
Feishu master draft: practical article first, reusable across channels
WeChat draft box: official API, draft only, manual publish
Images: real screenshots for proof, knowledge cards for structure
Post-publish flowback: record, recap, methodology, product material, Skill iteration
Minimum loop: 6 steps and one copyable prompt
Soft ending: access path, then ask what the reader can put into the workflow today
```

When explaining Codex + Obsidian:

```text
Obsidian vault folder = Codex project folder
```

When giving command blocks:

```text
Say clearly that the whole block can be copied to Codex / WorkBuddy.
```

### Title

Use one title only. Prefer:

```text
real result + key action + surprising mechanism
```

If there is a true business result, put it in the title.

Good patterns:

```text
我只说了5个字，一条内容开始在「AI工作台」里继续生长
一张截图，怎么变成一篇客户愿意看完、也能照着做的公众号文章
我把一次真实交付拆进知识库，后面写内容明显省劲了
```

Avoid empty poetic titles that hide the business value.

### Opening

If there is a result:

1. Show the result immediately.
2. Add proof image(s).
3. Explain why this result matters.
4. Connect result to the case in the article.

If there is no result:

1. State the main event directly.
2. Explain who should care.
3. Say what the reader can take away.

### Background

Explain the minimum context:

```text
What happened?
What materials were used?
What tools/platforms were used?
Why use these tools?
What problem was being solved?
```

For technical tools, translate first:

```text
One tool stores and organizes material.
One Agent reads, writes, analyzes, and executes.
```

### Customer-Safe Case Framing

When the source material contains real customers, students, private chats, payment proof, internal products, or local file paths, convert it into a safe public-facing frame before writing.

Use this pattern:

```text
who: practitioner / consultant / teacher / course creator / business owner / service provider
asset: core product / flagship offer / paid community / consulting service / training camp
action: what was improved, packaged, delivered, or automated
evidence: authorized screenshot, source text, public result, or clearly marked inference
boundary: do not expose names, private screenshots, exact revenue, rights, prices, or guarantees unless explicitly confirmed
```

For vertical AI digital employee / Skills matrix articles, the point is not to show off a tool. The point is to show how a professional turns repeatable expertise, delivery, product packaging, content production, and sales support into reusable AI workflows.

Do not turn one person's case into a universal promise.

### Live Action Chain

Use real actions:

```text
I gave the Agent this material.
I sent this short command.
The Agent generated this.
I reviewed it this way.
I sent the next status command.
The system produced these files/records.
```

Do not write only abstract workflow names.

### Breakdown

For every key step, write:

```text
Trigger: what the user says or does
Agent action: what the Agent performs
Output: what artifact is created
Business value: why this matters next time
Check: how the reader knows it worked
```

### Practical Copy Section

Give the reader short commands:

```text
第一句：请先帮我根据这些素材，判断最适合写成什么内容形态。
第二句：请先生成文章大纲，不要写正文。
第三句：请把每个步骤补成“动作、产物、检查标准”。
第四句：请检查哪里缺图、哪里缺证据、哪里对小白不友好。
```

### Stage Summaries

After complex sections, add a short recap:

```text
刚才这一段，我们只解决一个问题：先让工具和素材对上号。
接下来才是关键：让内容发完以后继续回流。
```

### Feishu / Platform Document Layout

If the output is a Feishu document, customer-facing document, or knowledge-base long article, add a stronger reading structure:

```text
Title area
One-screen conclusion
Manual table of contents
H1 / H2 / H3 layered body
Evidence images with captions
Overview knowledge card near the route-summary or synthesis section
Final risk/check callout
```

Do not let long screenshots dominate the document. Resize them so they work as evidence, and use paired-image layouts for comparable posters, before/after images, or two related cases.

### Integrated Image Order

Before adding new illustrations, place all usable uploaded, pinned, featured, and source-document images. Then add customer-specific Xiaohei illustrations only where the article still needs explanation, action guidance, a cognitive turn, a common pit, a workflow loop, or a synthesis image.

The final image plan should label every item as original image, real evidence, customer-specific Xiaohei Skill output, embedded-fallback Xiaohei output, or optional explanatory image.

### Ending

End with meaning and next action.

If product handoff is requested:

1. First summarize the core lesson.
2. Then lightly mention the course/service/community/tool.
3. Add contact only if appropriate for the platform.

The handoff must feel earned, not pasted.

### Post-Article Feishu Decision

After the complete article and final self-check, ask whether the user wants a new beautified Feishu document unless the current request already contains an explicit yes or no.

```text
文章已经生成完成。要不要继续把这篇文章创建为一篇新的飞书文档，并按飞书文档规范完成排版美化？
1. 需要，创建新的飞书文档并美化
2. 不需要，保留当前文章，不写入飞书
```

Do not perform a Feishu cloud write before this choice. If the user chooses no, end with the article only. If the user chooses yes, use `feishu-delivery-routing.md`.

## Tone

Use:

- Real operator voice.
- Precise business judgment.
- Beginner-friendly explanations.
- Light humor when natural.
- Occasional self-mockery or vivid phrasing.

Avoid:

- Empty trend talk.
- Generic “AI is changing everything”.
- Dense prompt-engineering language.
- Overly poetic short-line stacking.
- Hard-sell claims.
- Unverified guarantees.
